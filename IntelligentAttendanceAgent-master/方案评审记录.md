## 二、AI 评估结论

### 总体结论

**架构层面可行，无需推翻**。用 LangGraph StateGraph 做"确定性护栏节点 + LLM 节点"的受控流水线，相比 ReAct 自主循环更适合安全敏感的 Text-to-SQL，这个判断和 LangGraph 官方定位一致。剩余问题集中在**实现细节**和**若干设计缺口**，不影响立项，建议按下列意见修订后进入 P0。

### 一、版本与环境可行性（已核实）

| 项 | 核实结果 | 结论 |
|---|---|---|
| langgraph >= 1.0 | 当前最新 1.2.11，要求 Python >= 3.10 | ✅ 适用；`StateGraph / add_conditional_edges / compile(checkpointer=)` API 均有效 |
| Python 3.10.0（venv） | 满足最低要求 | ⚠️ 3.10.0 是 2021 年的初版补丁，建议升到 3.10 最新补丁或 3.11/3.12 |
| langgraph-checkpoint-postgres | 当前 3.1.2，依赖 psycopg **3**（非 2） | ✅ 但注意：首次必须调用 `.setup()`；手动传连接时必须 `autocommit=True` + `row_factory=dict_row`，否则报 TypeError |
| langchain-deepseek | 存在 v1.0.x，兼容 LangChain 1.x | ⚠️ 2026-05 有已知 issue（deepseek-v4-flash 二次调用 payload 400），建议锁定版本并 P0 做冒烟验证 |
| 连接驱动 | 全链路统一用 psycopg3 即可（SQLAlchemy 也用 psycopg3 方言） | 建议在选型表中明确写 psycopg3，避免装成 psycopg2 |

另外建议启用 `LANGGRAPH_STRICT_MSGPACK=true` 限制 checkpoint 反序列化类型——与方案的安全主题契合，且是官方推荐。

### 二、必修的设计缺口（高优先级）

1. **没有用户身份设计**。需求中有"**我**上周的加班审批通过了吗"，但方案没有 `current_user` 概念。需要在 state/config 注入当前用户（演示可固定为张三），否则：
   - "我"无法解析；
   - 6.1 提到防"越权试探"，但没有身份就无从判定"越权查他人考勤"。
   建议：state 增加 `user_id`，SQL 生成提示中固化"本人 = 张三；是否允许查他人"的口径。

2. **种子数据时间窗与"这个月/上周"冲突**。种子固定 2026-01，而演示时的系统时间不是 2026-01，问"我本月迟到几次"会查到空集。建议**种子脚本按运行当月动态生成日期**（相对日期偏移），静态示例仅作文档说明。

3. **"校验器自动附加软删除过滤"实现风险高**。给任意 LLM 生成 SQL 自动注入 `WHERE is_deleted=FALSE`，正则/字符串改写会在 CTE、JOIN、子查询、UNION 场景踩坑。建议改为**数据库视图**：建 `v_employee` 等视图（内含过滤条件），提示词强制"只允许查视图"，校验器只做**验证**（发现查询基表即拒绝），不做改写。这与只读角色一样属于"不依赖模型正确性"的兜底层。

4. **SQL 静态校验建议用 sqlglot 替代正则**。可确定性完成：单语句判定、语句类型（SELECT/WITH）、LIMIT 注入（AST 级，避免正则误判）。同时补黑名单缺口：
   - `SELECT ... INTO new_table`（会建表，现有黑名单挡不住）；
   - 函数级：`pg_read_file / pg_read_binary_file / pg_ls_dir / lo_import / lo_export / dblink / pg_sleep / pg_terminate_backend` 等；
   - 注意 PostgreSQL 存在**可写 CTE**（`WITH x AS (INSERT ... RETURNING)`），"以 WITH 开头"不等于只读，需按 AST 判断。
   只读角色能兜住大部分，但这层是面试演示点，值得做扎实。

5. **罚款/加班费等"规则推导值"不应交给 LLM 算**。迟到罚款档位（示例数据是 ≤10min 罚 5、11-20min 罚 10、21-30min 罚 20）、加班倍率、调休 1:1 等规则若让 LLM 写进 SQL 的 `CASE WHEN`，月汇总场景极易幻觉。建议：
   - SQL 只取**事实数据**（分钟数、次数、小时数）；
   - `postprocess_node` 用**确定性 Python 规则模块**计算金额（规则集中一处维护）；
   - 至少也要在生成提示中固化档位映射表 + 2~3 个 few-shot SQL。

6. **checkpointer 与只读连接必须分开**。方案只提了"只读角色"，但 `PostgresSaver` 需要**读写权限**建表和写 checkpoint。建议 P0 就建两个角色：`app_ro`（业务查询，仅 SELECT + 视图授权）、`app_rw`（仅 checkpointer 用），并明确 checkpoint 表所在 schema。

### 三、实现细节建议（中优先级）

1. **"混合"意图的并行汇合是坑**。制度分支与 SQL 分支节点数不同，`answer_node` 会被触发两次。简化建议：制度全文本来就在系统提示中，可将路由简化为"**是否走 SQL 分支**"，删掉独立 policy 分支，answer 单点汇聚——v1 能力不减，图更简洁；若保留双分支，需加 join 节点或在 answer 中检查完成标志。
2. **自动补 LIMIT**：聚合查询无需追加；明细查询提示词强制 `ORDER BY`（否则 LIMIT 结果不稳定）；限制追加次数防"越补越大"。
3. **`statement_timeout=3s` 偏激进**（首次连接、冷缓存），建议 5~10s 可配；建议通过连接 `options="-c default_transaction_read_only=on -c statement_timeout=5000"` 设置，而不是靠执行 SQL（`SET` 已在黑名单里，注意别自相矛盾）。
4. **执行前 EXPLAIN 估算**：3 人小数据集上无意义，建议做成配置开关，默认只对非聚合查询启用。
5. **多轮追问的 SQL 上下文**：第九节只讲了消息压缩，"那李四呢？"需要**上轮 SQL + 结果摘要**进入生成提示，建议明写。
6. **枚举值治理**：`staff_type / status / leave_type / overtime_type` 等建议加 CHECK 约束，并把这些允许值**注入 schema 描述给 LLM**（否则它写 `status='迟到'` 还是 `status='late'` 全凭运气）。
7. **时区**：连接与库统一 `Asia/Shanghai`，`TIME` 字段无法表达跨天（加班到次日）场景，演示够用但要注明。
8. **结果量控制在小数据上验证不了**：建议加一个可选批量灌数脚本（如 3 人 × 12 个月），用于演示 LIMIT/超时/字节上限真正生效。

### 四、种子数据勘误

- **`2026-01-10` 是星期六，不是周日**（2026-01-01 为周四）。"王五 01-10 周日加班"应改为 **01-11（周日）**，或干脆动态生成日期规避此类错误。
- 迟到罚款金额（5/20/10 元）隐含了档位规则，但方案未给出档位表——见第二部分第 5 条，需在制度提示中显式固化，否则数据与规则对不上时评测无法判定对错。
- `attendance_record.status` 枚举（正常/迟到/早退/缺卡/旷工）与"周日加班"记录行冲突，需明确周日是否应该在打卡表出现。
- 调休余额（加班获得 vs 请假消耗）目前没有明确计算口径，建议写成一条 join 规则文档化。
- 2026 春节日期标了"示例"，上线前按国务院通知校正即可（方案已有此意识）。
